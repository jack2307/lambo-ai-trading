# Measuring the rule instead of the ceiling: `np-brk-p4-m15` without a 4-hour cap

**Date:** 2026-10-07 (pre-registration; committed before the first config line
and before any cell on A' or B' was looked at)
**Question:** `docs/decisions/2026-10-06-news-entry.md` passed exactly one
registered rule through the desk's gate on two non-overlapping four-year
windows — and then disqualified it itself, because its registered invalidation
fired in **under 10%** of its trades: 80 to 97 of 90 to 118 trades left by the
engine's four-hour `max_hold_ms`. So the measured object was *"enter 45 minutes
after a high-impact USD release in the direction of the move so far and hold
four hours"*, not the one-impulse-range stop and 1.8R target that were
registered. **Does the registered geometry pass the gate when the ceiling is no
longer the binding constraint? And is this rule's direction distinguishable
from a coin flip?**
**Outcome:** open. This file is the registration, not the result.

## 1. Hypothesis, in one sentence

The edge in `np-brk-p4-m15` comes from the **registered rule** — one
impulse-range stop, 1.8R target, entry at +45 min with the sign of the impulse
— and therefore survives the removal of the four-hour cap; and its direction is
outside the distribution of the same entries with random sides.

**Prediction, stated so it can come back no:** it does **not**. The row passes
at 4 hours and only at 4 hours, because a four-hour clock on a post-release
hold is itself the mechanism (mean hold 240.5 min on the A' row, i.e. the cap),
and the one-impulse-range stop — median **5.03 ATR(14) = 23.02 points** — is so
far away that it is nearly unreachable inside the horizon the engine allowed.

## 2. Falsifier — specific, and it can fire

**F1 (the ceiling falsifier).** `np-brk-p4-m15` passes the gate (PF >= 1.200
AND expectancy >= +0.050R AND >= 40 trades, on **both** A' and B', in the
**same** guard arm) at the 4-hour cap, and **fails it at every cap level where
TIMEOUT is no longer the majority exit reason**. If F1 fires, the registered
stop/target geometry is **not** what produced the number, the real finding is
*"hold four hours in the direction of the move after a release"*, and that is a
**different rule** which must be registered under its own name before any
number is quoted for it. It may not be sold as the geometry of
`2026-10-06-news-entry.md` §4.

**F2 (the direction falsifier).** `--mode=null-dir` on the same row, same
filter, same parameters: the same entries with each side re-drawn by coin flip
(`DirectionFlipped` mirrors stop and target about the signal bar's close, so
the stop *distance* is held and only the side moves). If the row's profit
factor sits **below the 95th percentile** of that distribution on **either**
window, its direction has not been distinguished from a coin flip on that
sample.

**The conclusion both share, declared now so it cannot be softened later:** if
**F1 or F2 fires**, then the only non-zero result of six closed programmes and
~5,400 cells **is not a method**, and that — negative — is the most important
thing measured tonight.

**What would make the hypothesis survive instead:** the row passes the gate on
both windows at a cap where STOP + TARGET are the majority of exits, **and**
the direction null reads >= 95th percentile on both windows. Then the row moves
from "not a candidate" to "candidate pending a second instrument, a second
timeframe and a fill model", which is still not a position.

## 3. How the ceiling is moved: config, not code

`max_hold_ms` is a per-market override (`crates/fd-core/src/config.rs:385`,
applied at `config.rs:499`, read into the engine at
`crates/fd-backtest/src/engine.rs:323` as
`spec.trading.max_hold_ms.unwrap_or(config.trading.max_hold_ms)`). So the scan
needs **no build**: four sibling config directories, each a copy of `config/`
with **one line** added under `[markets.xauduka.trading]`, the way `agent/m2`
did it:

| arm | directory | line added | hours |
|---|---|---|---|
| control | `config/` (untouched) | none | 4 |
| | `config-h8/` | `max_hold_ms = 8640000` | 8 |
| | `config-h24/` | `max_hold_ms = 86400000` | 24 |
| | `config-h168/` | `max_hold_ms = 604800000` | 168 |
| | `config-nocap/` | `max_hold_ms = 0` | **none at all** |

`0` is not "zero hours": `engine::check_exit` only applies the clock when
`max_hold_ms > 0`, and `search.rs:337` prints
`max hold: none — positions run to a stop, a target or the end of data`. That
arm is the one where the registered geometry is the **only** invalidation, and
it is the arm F1 is really asked on.

`config/default.toml` is **not edited**, so
`crates/fd-backtest/tests/trading_rules.rs:67` still asserts four hours for
every market the shipped config declares, every receipt published before
tonight stays reproducible, and the two funded books on account 33708517 are
untouched. No code is compiled; the shared binary
`/e/rust/fd-n1bin/target/release/search.exe` is used as §2 of the brief directs.

## 4. Rows — four of twelve, and why not all twelve

`receipts/newsgeom-rows.toml` carries the **four probe-4 rows** of
`receipts/news-entry.toml`, copied byte for byte (label, base, filter,
overrides, why): `np-brk-p4-m05`, `np-brk-p4-m15`, `np-rev-p4-m05`,
`np-rev-p4-m15`. Nothing is re-specified and no parameter, filter or threshold
is changed.

The probe-1 and probe-2 rows are excluded **on purpose**: their own exits
already fire (`np-brk-p1-m05` reads STOP 37 / TARGET 12 / TIMEOUT 55), they are
not the rows the ceiling question is about, and they take **0 trades on 8 of 12
rows** under the desk's guards anyway. Giving them four more ceilings would be
32 further chances for some row to clear 1.200 — the multiple-testing tax this
record series exists to refuse.

The two reversion rows stay in because they are the **direction mirror**: the
same entries with the side flipped by construction. If PF 1.636 -> 0.560 does
not still invert at a long cap, the direction claim is weaker than n1 published.

## 5. Windows — A' and B', unchanged

`xauduka` 15m from `/e/rust/flowdesk/data` (read-only), exactly n1's two
non-overlapping windows, so the result is comparable row for row:

- **A'** `--from=2022-01-01 --to=2026-01-01` (127 USD impact-3 events)
- **B'** `--from=2018-01-01 --to=2022-01-01` (134 USD impact-3 events)

No third window is introduced, no window is extended, and the brief's own
3-month windows are not used: §6 of `2026-10-06-news-entry.md` counted 8 and 9
events in them against a 40-trade floor, and that arithmetic has not changed.

Both guard arms on every cap level (brief §4(ii)): `--guards` and no `--guards`,
reported side by side. `--exit-mix` on **every** run, and the **percentage of
exits by reason** printed for every cell — that is the measurement, not a
footnote.

2. **Is `--samples=` read in `--mode=null-dir`?** Yes — the brief's §4(iv)

The 4-hour level of the ceiling scan is simultaneously the **control** and a

The real `(run, row)` count is published at the end against this number. Any
cell beyond it goes in a **dated note appended to this file**, never by editing
a line above.

## 8. How it is read — thresholds, floors and what is withheld

- **Gate, not adjustable:** PF >= 1.200 AND expectancy >= +0.050R AND >= 40
  trades, on **both** A' and B' in the **same** arm. One window is nothing.
  Under ~40 trades: **no conclusion**, whatever the profit factor says.
- **Expectancy is read, and so is PF.** Brief §4(i): `expectancy` and `total_r`
  are blind to swap. `[markets.xauduka.trading]` sets
  `swap_long_per_lot = swap_short_per_lot = 0.0` and n1's receipts print
  `swap: long 0.00 / short 0.00 USD per lot per night`, so on **this market**
  the two legs cannot diverge for that reason. Raising the cap to 24 h and 168 h
  makes positions cross sessions, so the printed `swap$` column is quoted for
  every long-cap cell: if it is ever non-zero, expectancy becomes unreadable on
  that cell and PF is the only leg quoted.
- **Exit mix is the measurement.** Every cell reports STOP / TARGET / TIMEOUT /
  NEWS_FLAT / WEEKEND_FLAT / END_OF_DATA as **counts and percentages**. A cell
  in which TIMEOUT is still the **majority** of exits is labelled
  "**ceiling-bound**" and its pass is reported as a pass *of the ceiling*, not
  of the geometry. That label is descriptive arithmetic (> 50% of trades), not
  a threshold anyone may move.
- **Guarded arm at long caps is expected to mutate the rule.** The desk's guard
  prints `news flat 60/30 (impact>=3, USD)`. At a 4-hour cap it closed 1 of 96
  trades; at 24 h or more a position will frequently still be open when the next
  release approaches, so NEWS_FLAT becomes a real exit and the guarded arm
  measures a **third** rule ("hold until the next release"). If NEWS_FLAT
  exceeds STOP + TARGET on a guarded cell, that cell is reported as measuring
  the guard, not the geometry. `[trading.guards]` is **not** touched.
- **Percentile is withheld when it is not calibrated.** Brief §4(v):
  `matched_rate` probes once at `entryRate = 0.02` and scales linearly, and
  n1's own A'/B' rows read count match **1.28** — outside
  `COUNT_MATCH_BAND = 0.25`. Every cell's count match is printed; any cell
  outside the band has its percentile reported as **unmatched and withheld**,
  with the gate alone carrying it. `null p50` is written beside any percentile
  that *is* quoted, because the desk's median null has PF 0.867.
- **Direction null:** `--samples=4000`, `--null-sides=coin` (the default and
  the null every published percentile was read against). >= 95th percentile =
  outside its own null; below = not distinguished from a coin flip on that
  sample. The tool's own wording, not a new threshold. The null is run at each
  cap level because the cap changes the trades it permutes.
- **`wrong_side_stop` (brief §4(vi)):** if any cell prints it non-zero, that
  cell is **not readable** and is reported, not repaired.
- **Cost:** `spread = 0.28` from config on every cell, and the
  `cost-matched null: ... cost X% of R` line the tool prints is quoted with the
  stop size beside it. No spread fan is re-run: n1 measured the break point at
  0.56 to 1.12 and the live log's worst spread at +45 to +60 min as 0.260, and
  nothing in this registration changes the entry minute. A longer hold changes
  nothing about the one spread paid per round trip.

## 9. What this will not say

- Nothing here measures a second instrument, a second timeframe, limit entries,
  or the slippage of a market order at a release. n1's disqualifications on
  those points stand whatever happens tonight.
- Nothing here is a search for a better cap. Five levels are declared, all five
  are published, and a pass at exactly one of them is reported as the ceiling
  finding of F1 — not as the discovery of an optimal horizon.
- If F1 fires, this file does **not** register the four-hour hold rule. It
  names it as a separate registration someone else has to write, and it will
  carry its own direction null, its own windows and its own multiple-testing
  ledger.

## Note added 2026-10-07, after the first scan pass and BEFORE its numbers were read

Append-only; no line above is altered.

**An arithmetic slip of mine, and what was done with it.** The `config-h8/`
directory of §3 was written with `max_hold_ms = 8640000`. That is **2.4 hours**,
not 8 — 8 h is 28,800,000 ms. The run printed
`max hold: 2.400 h (8640000 ms)` in its own header, which is how it was caught:
the header line §3 added for exactly this purpose did its job.

Sixteen cells (4 rows x 2 windows x 2 guard arms) were therefore computed at a
cap of **2.4 h, TIGHTER than the 4-hour control**. No outcome number from them
has been looked at at the time this note is written — only the `max hold:`
header line of each file. Two choices were available: delete them unread, or
declare the level and keep it.

**They are kept, and the level is declared**, because a cap *tighter* than the
control is a direct test of F1 in the other direction: if the row reads *better*
at 2.4 h than at 4 h, then the clock is even more plainly the mechanism. Throwing
that away to keep the ledger tidy would be destroying measured evidence.

Added to §3 and §7, counted, nothing else changed:

|---|---|---|---|
| | `config-h2.4/` | `max_hold_ms = 8640000` | 2.4 (tighter than the control) |
| | `config-h8/` | `max_hold_ms = 28800000` | 8 (the level §3 meant) |

| ledger line | cells |
|---|---|
| declared in §7 | 96 |
| 2.4 h level retained: 4 rows x 2 windows x 2 arms | +16 |
| 8 h level re-run at the correct 28,800,000 ms: 4 rows x 2 windows x 2 arms | +16 |
